This service turns a plain English question into a SPARQL query that api-gateway then runs against GraphDB.

**How it works**  
We give the LLM three things every time someone asks a question:  
1. **A description of the schema** - what classes exist (Patient, Visit, Diagnosis, etc.), how they relate, and what fields each one has. This used to be typed out by hand and it went stale (it still mentioned a Complaint class that doesn't even exist in the data anymore). Now it's generated by actually querying GraphDB, so it can't drift out of sync like that again.  
2. **A handful of example questions with their correct SPARQL** - we keep a growing list of real, verified NL → SPARQL pairs (scripts/data/nl2sparql_examples.json). For every incoming question we find the 5 most similar ones from that list and hand them to the LLM as examples to follow. This is the "RAG" part - nothing fancier than that.  
3. **A short list of gotchas** - things about this dataset that are easy to get wrong, like some fields that look numeric but are actually stored as text, or dates that are unreliable strings instead of real dates. Just a cheat sheet, hardcoded in main.py.  
After the LLM answers, we double check it didn't invent a predicate or class that doesn't exist (this used to happen silently and just return zero results, which is worse than an error). If it made something up, we ask it to fix it once. If it still can't, we say so instead of pretending everything's fine.  

**Folder layout**  
scripts/  
   embedding_config.py   -> shared settings (model name, file paths). Both sides below import from here.  
   data/                 -> the actual files. Not code, just data.  
   offline/              -> scripts you run by hand, never run by the service itself  
   runtime/              -> code the running service actually imports and uses  
   
The split is basically: **offline = stuff a person runs on their laptop to regenerate a file. runtime = stuff that runs every time someone hits ** **/translate** **.**  
**When you add a new example query**

When you write a new NL → SPARQL pair and confirmed it actually works against GraphDB, follow this to get it into the system:  
1. Add it to scripts/data/nl2sparql_examples.json.  
2. Run this from the nl2sparql/ folder:
```python -m scripts.offline.refresh_examples```  
 This re-embeds all the examples and regenerates the .md file that mirrors them for humans to read.

3. Rebuild and restart the container:  
```docker compose build nl2sparql && docker compose up -d nl2sparql```  
  
If you forget step 2, the service will actually refuse to start (it checks the embeddings file and the examples file have the same number of rows), so it's hard to mess this up silently.

**When the GraphDB schema changes**  
New predicate, new class, a new month's data dropped in - Run:  
```python -m scripts.offline.generate_ontology_snapshot```
   
This talks to GraphDB and rewrites scripts/data/ontology_block.txt (the schema description that goes into the prompt) and known_schema.json (used for the "did the LLM make something up" check). Worth actually reading the diff on ontology_block.txt since it goes straight into the prompt - make sure nothing weird slipped in.  
Then rebuild/restart same as above
